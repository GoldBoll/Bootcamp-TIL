# 2026-07-28 언리얼 어서션 3형제 — check·verify·ensure

팀 스터디에서 공유된 `check`/`verify`/`ensure` 정리 글을 출발점으로, 엔진 헤더(UE 5.8)로 사실을 대조하고 우리 팀 프로젝트(협동 이사 게임) 소스를 실측해 적용 기준을 정했다. 발행본: [/posts/til-ue-assertion-macros/](/posts/til-ue-assertion-macros/) — **개념 정리(1~4항)만 발행**했고, 프로젝트 실측·트러블슈팅(5~7항)은 글을 분리하기로 해 발행에서 제외했다.

## 오늘 한 일 요약

1. **개념 대조** — 셋을 가르는 축을 "실패 시 반응 × 컴파일 아웃 시 식 평가 여부" 2축으로 재정리. `Misc/AssertionMacros.h` 실측: `DO_CHECK==0`에서 `check(expr)` → `{ CA_ASSUME(expr); }`, `CA_ASSUME` 기본 정의는 `((void)sizeof((bool)(Expr)))`라 **식이 실행되지 않는다.** `verify`는 `{ if(UNLIKELY(!(expr))){ CA_ASSUME(false); } }`로 식 평가 유지.
2. **정정 1 — `ensure`도 식이 남는다.** `DO_ENSURE==0`에서 `#define ensure(expr) (LIKELY(!!(expr)))`. 반환값까지 그대로라 `if (!ensure(X)) return;` 관용구는 모든 빌드에서 흐름이 동일하다. "식이 유지되는 건 verify뿐"이라는 통념이 틀렸다.
3. **`ensure` 1회 리포트의 구현** — `UE_ENSURE_IMPL`은 `LIKELY(!!(expr)) || (...)` 단락 평가 식(=bool). 억제 플래그는 `bGEnsureHasExecuted<FileLineHashForEnsure(__FILE__, __LINE__)>` — 파일 경로+줄 번호를 djb2 해시로 묶은 템플릿 `std::atomic<uint8>`. 즉 호출 지점 단위. `ensureAlways`는 `bAlways=true`로 무시.
4. **정정 2 — Test 빌드에서도 꺼진다.** `Misc/Build.h`: Debug(1/1/1) · Development(1/1/0) · **Test(`USE_CHECKS_IN_SHIPPING`/`USE_ENSURES_IN_SHIPPING`/0)** · Shipping(동일). 기본값 `USE_CHECKS_IN_SHIPPING 0`, `USE_ENSURES_IN_SHIPPING = USE_CHECKS_IN_SHIPPING`. UE 5.0 헤더도 동일 → 최근 변경 아님. 켜기: `TargetRules.bUseChecksInShipping` → UBT가 `USE_CHECKS_IN_SHIPPING=1` 주입(`UEBuildTarget.cs`). `DO_GUARD_SLOW`는 Debug만 1.
5. **우리 코드 실측**(게임플레이 모듈 201개 파일) — `checkf` 2건(`TCPlayerCharacter.cpp` BeginPlay: PC·EnhancedInputLocalPlayerSubsystem), `check`/`verify`/`ensure` **0건**. 대신 `IsValid()` 46건 · 조기 반환 가드 73곳 · `UE_LOG` 356건. 두 `checkf`는 판정만 있고 부작용이 없어 컴파일 아웃돼도 동작이 안 바뀜(대신 Shipping에서 다음 줄 `PC->GetLocalPlayer()`는 무방비 — `check`를 쓰며 감수하는 부분).
6. **실전 사례** — `TCSessionFlow.cpp`: 클라이언트 접속 상태에서 방 생성 시 `?listen` ServerTravel이 클라 월드에서 불가 → 엔진 `ensure("Server travel should never create a pending net game")`까지 감(PIE 클라 인스턴스 실측). `ensure`라 세션이 죽지 않고 지점을 짚어 줬고, 수정은 어서션 추가가 아니라 `NetMode == NM_Client` 가드 + `SetPhase(Failed, "이미 다른 세션에 접속 중입니다")` 정상 분기.
7. **소크 지표의 전제 정리** — 어젯밤 소크(3h12m·1,877사이클·로그 238,095줄 전수 스캔)와 2인 네트워크 소크(270사이클)의 통과 기준 첫 줄이 `Ensure/Assertion/Error 0건`. ①중간 집계 12건은 제품 로그가 아니라 하네스 `LogPython: Error` 혼입 → 카운터 분리 후 제품 기준 0건. ②이 판정은 Development(에디터 PIE)에서만 유효 — 우리 `TeamCarry.Target.cs`에 `bUseChecksInShipping`이 없어 Shipping 패키지에선 `ensure`가 통째로 빠진다.

## 오늘 배운 것 정리

1. **식이 사라지는 건 `check` 하나뿐** — `verify`도 `ensure`도 컴파일 아웃 시 식은 평가된다. 부작용 있는 호출을 조건에 넣어야 하면 `check`는 금물.
2. **`ensure`는 값을 돌려주는 식** — `if (!ensure(X)) return;`이 성립하고, 리포트가 빠지는 빌드에서도 분기가 그대로 산다. 억제는 파일+줄 단위라 매 프레임 코드에도 안전하지만, 재현 횟수를 세려면 `ensureAlways`.
3. **어서션이 살아 있는 빌드는 기본값에서 Debug·Development뿐** — Test를 "어서션 있는 최적화 빌드"로 착각하면 안 된다.
4. **선택 기준은 치명도가 아니라 "플레이 중 도달 가능한가"** — 도달 불가(불변식) → `checkf` / 도달 가능+조용히 넘기면 안 됨 → `ensure` + 조기 반환 / 사용자에게 알려야 함 → 분기와 UI. 우리 코드에 어서션이 적은 건 실패 대부분이 네트워크 타이밍 등 도달 가능한 상태이기 때문.
5. **역할 분담** — 어서션은 "있으면 안 되는 상태", 검증 전용 로그(`TC.FixVerify.Debug`, 서버/클라 태그 대조)는 "있어도 되는데 값이 맞아야 하는 것". 섞으면 어서션이 시끄러워지고 곧 무시된다.
6. **어서션 개수를 지표로 쓰려면 정의가 함께 있어야 한다** — 무엇을 세는지(제품 vs 하네스), 어느 빌드에서 세는지. 둘 중 하나만 빠져도 "0건"은 품질이 아니라 착시다.
