## 나누어 떨어지는 숫자 배열 (Lv.1)

> 문제: <https://school.programmers.co.kr/learn/courses/30/lessons/12910>

`vector<int> arr`에서 `divisor`로 나누어 떨어지는 원소만 골라 오름차순으로 정렬해 반환한다. 하나도 없으면 `[-1]`을 반환한다. 제한은 넉넉한 편이다 — `arr` 길이 1~100, 원소는 100 이하의 자연수, `divisor`는 1~10.

| arr | divisor | return |
| --- | --- | --- |
| [5, 9, 7, 10] | 5 | [5, 10] |
| [2, 36, 1, 3] | 1 | [1, 2, 3, 36] |
| [3, 2, 6] | 10 | [-1] |

접근은 단순하다. `%` 연산자로 나누어 떨어지는 원소를 필터링하고, 결과를 `sort()`로 오름차순 정렬한다. 주의할 점은 하나다 — 결과가 비어 `-1`을 넣었을 때는 정렬하면 안 되므로 `else`로 분기해야 한다.

### 풀이 1 — for 루프 + sort (작성한 코드)

```cpp
#include <string>
#include <vector>
#include <algorithm>
using namespace std;

vector<int> solution(vector<int> arr, int divisor) {
    vector<int> answer;

    for (size_t i = 0; i < arr.size(); i++)
    {
        if(arr[i] % divisor == 0)
        {
            answer.push_back(arr[i]);
        }
    }

    if(answer.size() == 0)
    {
        answer.push_back(-1);
    }
    else
    {
        sort(answer.begin(), answer.end());
    }

    return answer;
}
```

### 풀이 2 — copy_if + sort (STL 활용)

`copy_if(first, last, dest, pred)`는 조건을 만족하는 원소만 `dest`로 복사한다. `back_inserter(v)`가 `v.push_back()`을 호출해 주는 출력 이터레이터를 만들어 주고, 람다 `[divisor](int x){ return x % divisor == 0; }`가 divisor를 캡처해 조건을 판별한다. 빈 벡터 검사도 `size() == 0` 대신 `empty()`를 쓰면 의도가 더 분명하다.

```cpp
#include <string>
#include <vector>
#include <algorithm>
#include <iterator>
using namespace std;

vector<int> solution(vector<int> arr, int divisor) {
    vector<int> answer;

    copy_if(arr.begin(), arr.end(), back_inserter(answer),
            [divisor](int x){ return x % divisor == 0; });

    if(answer.empty())
    {
        answer.push_back(-1);
    }
    else
    {
        sort(answer.begin(), answer.end());
    }

    return answer;
}
```

두 풀이 모두 시간복잡도는 O(n + k log k)로 같다(k = 나누어 떨어지는 원소 수, 필터링 O(n) + 결과 정렬 O(k log k)). 풀이 2는 for 루프를 `copy_if` 한 줄로 대체해 코드가 더 간결할 뿐이다. 참고로 `sort(first, last)`는 기본이 오름차순이고, 내림차순은 `sort(answer.begin(), answer.end(), greater<int>())`처럼 비교자를 넘긴다.

### 복기

- `%` 연산자로 나누어 떨어지는 조건 필터링
- 결과 없을 때 `[-1]` 반환 처리 필수 — `-1` 삽입 후에는 정렬하지 않도록 `else` 분기
- `copy_if` + `back_inserter`로 for 루프 대체 가능
- `size() == 0` 대신 `empty()`가 더 관용적

## 백준 9012 - 괄호 (Silver IV)

> 문제: <https://www.acmicpc.net/problem/9012>

`'('`와 `')'`로만 이루어진 문자열이 올바른 괄호 문자열(VPS)인지 판단한다. 짝이 정확히 맞으면 `YES`, 아니면 `NO`를 출력한다. 테스트 케이스는 최대 50개, 문자열 길이는 2~50이다.

| 입력 | 출력 |
| --- | --- |
| (())() | YES |
| (())()) | NO |
| (()())((())) | YES |
| (((()())() | NO |

괄호 문제는 스택으로도 풀 수 있지만, 여는 괄호에 +1·닫는 괄호에 -1을 하는 `balance` 카운터만으로 충분하다. 순회 중 `balance`가 음수가 되는 순간은 닫는 괄호가 여는 괄호보다 먼저 나온 것이므로 즉시 `NO`, 끝까지 돌고 `balance == 0`이면 `YES`다. 홀수 길이거나, 첫 문자가 `'('`가 아니거나 마지막 문자가 `')'`가 아니면 순회할 필요도 없이 `NO`라서 조기 탈출을 넣었다.

문자열 처리는 `front()`/`back()`으로 인덱스 접근 없이 양 끝 문자를 확인하고, 범위 기반 for로 char 단위 순회했다.

### 풀이 — balance 카운터 (작성한 코드)

시간복잡도 O(n) — 문자열 한 번 순회.

```cpp
#include <iostream>
#include <string>
using namespace std;

string solution(string s)
{
    if(s.size() % 2 != 0) return "NO";
    if(s.front() != '(' || s.back() != ')') return "NO";

    int balance = 0;
    for(char c : s)
    {
        if(c == '(') balance++;
        else balance--;

        if(balance < 0) return "NO";
    }
    return (balance == 0) ? "YES" : "NO";
}

int main()
{
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int T;
    cin >> T;
    while(T--)
    {
        string s;
        cin >> s;
        cout << solution(s) << "\n";
    }
    return 0;
}
```

### 복기

- 괄호 문제는 스택 또는 balance 카운터 두 방법 모두 가능
- `balance < 0`이 되는 순간 = 닫는 괄호가 먼저 나온 것 → 즉시 NO
- 최종 `balance != 0` = 열린 괄호가 남아있는 것 → NO
- 홀수 길이 조기 탈출은 선택이지만 코드 의도가 분명해짐

## 백준 10828 - 스택 (Silver IV)

> 문제: <https://www.acmicpc.net/problem/10828>

정수를 저장하는 스택을 구현하고 `push X`, `pop`, `size`, `empty`, `top` 명령을 순서대로 처리하는 문제다. 명령은 최대 10,000개, X는 절댓값 2³¹ 미만의 정수다.

| 명령어 | 출력 |
| --- | --- |
| push 1 | |
| push 2 | |
| top | 2 |
| size | 2 |
| empty | 0 |
| pop | 2 |
| pop | 1 |
| pop (비어있을 때) | -1 |
| empty | 1 |

`stack<int>`를 그대로 쓰면 각 명령이 O(1)이라 전체 O(N)이다. 대신 STL 스택의 규칙 두 가지를 지켜야 한다. `pop()`은 반환값이 없으므로 값을 읽으려면 `top()`을 먼저 호출하고 그다음 `pop()`한다. 그리고 빈 스택에서 `pop()`·`top()`을 호출하면 Undefined Behavior(표준이 결과를 정의하지 않는 동작)라서, 문제 요구대로 `empty()`를 먼저 확인해 비어 있으면 `-1`을 출력했다. 명령어는 `string`으로 읽어 `cmd == "push"`처럼 `==`로 비교했다.

### 풀이 — stack&lt;int&gt; 활용 (작성한 코드)

```cpp
#include <iostream>
#include <stack>
#include <string>
using namespace std;

int main() {
    ios_base::sync_with_stdio(false);
    cin.tie(NULL);
    cout.tie(NULL);

    int n;
    cin >> n;

    stack<int> s;
    string cmd;

    for(int i = 0; i < n; i++) {
        cin >> cmd;
        if(cmd == "push") {
            int num;
            cin >> num;
            s.push(num);
        }
        else if(cmd == "pop") {
            if(s.empty()) cout << "-1\n";
            else {
                cout << s.top() << "\n";
                s.pop();
            }
        }
        else if(cmd == "size") { cout << s.size() << "\n"; }
        else if(cmd == "empty") { cout << s.empty() << "\n"; }
        else if(cmd == "top") {
            if(s.empty()) cout << "-1\n";
            else cout << s.top() << "\n";
        }
    }
    return 0;
}
```

`cout.tie(NULL)`은 `cout`과 `cin`의 버퍼 동기를 해제하는 것으로, 대량 출력 시 속도 차이가 있다.

### 복기

- STL `stack::pop()`은 반환값 없음 → 값을 읽으려면 `top()` 먼저, 그다음 `pop()`
- 빈 스택에서 `pop()`·`top()` 호출은 UB → 문제 요구대로 `-1` 출력 처리 필수
- `empty` 명령은 비어있으면 `1`, 아니면 `0` 출력

## 언리얼에서 VS vs Rider — IDE 선택과 사용 경험

> 언리얼에서 C++ 클래스를 생성할 때 VS와 Rider가 구체적으로 어떻게 다른지 직접 비교

### 문제 상황

언리얼 클래스 마법사로 새 C++ 클래스를 만든 직후, VS에서 자동완성과 오류 표시가 바로 작동하지 않았다. 파일 자체는 프로젝트에 추가되는데 IDE가 완전히 인식하기까지 솔루션 재로드가 필요한 경우가 있었고, 그래서 "VS에서는 안 된다"는 인상이 남아 Rider를 함께 쓰게 됐다.

### 배운 점

VS에서도 클래스 생성 자체는 정상이다. 파일이 솔루션에 추가되고 언리얼에도 반영된다. 다만 생성 직후 인텔리센스(자동완성·오류 표시)가 즉시 따라오지 않을 수 있고, 솔루션을 재로드해야 IDE 기능이 정상화되는 경우가 있다. 대신 디버깅 환경은 확실한 강점이다 — 중단점, 호출 스택, 변수 확인 흐름이 익숙하고 안정적이다.

Rider는 `.uproject` 기준으로 프로젝트를 관리해서 새 파일 추가 후 반영이 빠르다. 생성 직후에도 자동완성·코드 인식이 자연스럽게 붙어서 "추가하고 바로 이어서 작업"하기 편했다.

공통적으로, 런타임 에러가 나면 처음엔 엔진 내부 파일 경로만 보여 당황할 수 있는데, 호출 스택을 따라가면 내 코드의 정확한 줄 번호를 찾을 수 있다.

### 결론

| 상황 | 추천 | 이유 |
| --- | --- | --- |
| 새 C++ 클래스 추가 후 바로 작업 | Rider | 생성 직후 코드 인식·자동완성이 빠르게 붙음 |
| 디버깅 / 빌드 흐름 | VS | 중단점·호출 스택 등 디버그 환경이 손에 익음 |
| 자동완성이 안 붙을 때 | VS 솔루션 재로드 | 파일 추가 직후 인텔리센스 반응이 늦을 수 있음 |

> **핵심 교훈**: "VS에서 클래스 생성이 안 된다"가 아니라, 생성 후 IDE 기능이 붙는 **속도**의 차이였다.
> 클래스 추가·즉각 작업은 Rider, 디버깅·빌드는 VS — 상황에 맞게 병행하는 것이 효율적.

> **오늘 배운 것** — 괄호 짝 검사는 스택 없이 balance 카운터로 O(n)에 끝난다(음수가 되는 순간 즉시 NO, 끝에서 0이면 YES). 그리고 "VS에서 클래스 생성이 안 된다"는 기능의 문제가 아니라 생성 직후 IDE 인식이 붙는 속도의 차이였다.
