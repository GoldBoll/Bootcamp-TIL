> 하루가 두 개의 긴 삽질로 나뉘었다. 오전에는 **라이팅 빌드**가 벽을 새까맣게 태우거나 지글거리게 만들었고, 오후에는 **로비에서 스테이지로 다 같이 입장하는 것 자체가 안 됐다**. 둘 다 "증상에서 원인이 곧바로 보이지 않는" 부류였고, 결국 둘 다 **격리 실험**으로 범인을 특정했다. 라이팅 쪽은 세 겹의 원인을 순서대로 벗겨냈고, 멀티 쪽은 "로딩을 개선하려고 넣은 최적화"가 범인이었다.

## 1. 라이팅을 구웠더니 벽이 타버렸다

**증상**: 라이팅 빌드를 돌리자 실내 벽이 균일한 주황색 덩어리가 됐다. 명암이라고 부를 게 아예 없다.

![라이트맵을 구운 직후 — 벽이 통째로 타버렸다](/assets/img/posts/2026-07-20/bake_burned.png)
*구운 직후. 그라데이션도 그림자도 없이 벽 전체가 한 덩어리로 뭉갰다*

빌드 로그가 단서를 줬다.

```
LightingResults: Warning: Extrude_233CC0FA Object has overlapping UVs.
LightingResults: Extrude_233CC0FA Lightmap UV are overlapping by 52.5%.
```

겹침률이 50~85%. 처음엔 "메시 UV가 깨졌구나" 싶었는데, 메시 설정을 열어보니 정반대였다. `Generate Lightmap UVs`는 **켜져 있었고** 채널 1에 제대로 패킹된 UV를 만들고 있었다. 문제는 그걸 안 쓰고 있었다는 것이다.

```
lightMapCoordinateIndex = 0   // ← 타일링용 텍스처 UV를 라이트맵으로 쓰는 중
```

**UV 채널 0은 텍스처를 반복시키려고 일부러 겹치게 만든 채널**이다. 그걸 라이트맵으로 지정하면 벽 A의 빛이 벽 B 자리에 기록된다. 빛이 서로 다른 면으로 새어 들어가니 전체가 평평하게 타버린 것이다. 인덱스를 1로 바꾸자 벽에 그라데이션이 돌아왔다.

여기서 한 번 헛발을 짚었다. 겹침 경고에 뜬 14개 메시만 고쳤는데, 실제로는 **레벨 전체가 같은 문제**를 갖고 있었다. 경고는 "가장 심한 것"만 뽑아 보여줄 뿐이었다. 레벨의 모든 스태틱메시를 훑어 인덱스와 해상도를 한 번에 정리해야 했다.

## 2. 얼룩은 잡았는데 이번엔 지글거린다

벽은 살아났지만 천장과 벽 경계에 검은 점이 뿌려졌다.

![간접광 노이즈가 셀 셰이더에 증폭돼 점박이로 보인다](/assets/img/posts/2026-07-20/bake_speckle.png)
*해상도는 충분한데(약 2uu/텍셀) 그림자 경계마다 점이 낀다*

간접광 샘플 부족이라 보고 품질을 올렸다. `Indirect Lighting Quality`를 2 → 6 → 8까지, 빌드 시간이 13분까지 늘어났는데도 **점이 그대로였다**. 샘플을 8배로 늘려도 안 사라진다는 건 계산 노이즈가 아니라는 뜻이다.

여기서 방향을 틀어 격리 실험을 했다. **포스트 프로세스를 끄고 찍어봤다.** 우리 프로젝트는 툰 셰이딩을 화면 전체에 얹기 때문에, 셀 셰이더가 미세한 밝기 차이를 밴딩으로 증폭할 가능성이 있었다. 결과는 예상 밖이었다 — PP를 꺼도 점이 그대로였다. 셰이더가 아니라 **라이트맵 자체에 그 노이즈가 구워져 있었다**.

그래서 두 번째 격리 실험을 했다. **레벨의 모든 조명을 Movable로 바꾸고** 다시 빌드했다. 구울 정적 조명이 하나도 없으니 라이트맵도 사실상 비게 된다.

![모든 조명을 Movable로 전환한 뒤 — 점이 완전히 사라졌다](/assets/img/posts/2026-07-20/bake_clean.png)
*구운 조명을 걷어내자 지글거림이 즉시 사라졌다*

점이 깨끗하게 사라졌다. 원인이 라이트맵이라는 게 확정됐다.

조사 중에 왜 그런지도 드러났다. 이 레벨의 벽·기둥·천장이 **전부 같은 `Cube` 메시 하나를 스케일만 바꿔 쓰고 있었다**(Cube14, Cube37, Cube64, Cube84…). 공유 메시는 라이트맵 UV 레이아웃도 공유한다. 1000uu짜리 벽과 240uu짜리 기둥이 같은 UV 배치를 나눠 쓰는 구조에서는, 컴포넌트별 해상도로 아무리 보정해도 균일한 품질이 나오지 않는다.

## 3. 결론은 "굽지 않기"였다

최종적으로 채택한 구성은 하이브리드다.

| 조명 | 모빌리티 | 이유 |
|---|---|---|
| PointLight | Movable | 실시간이라 항상 켜져 있고 캐릭터·운반 가구도 비춘다 |
| RectLight / SpotLight | Movable | 구우면 지글거림이 돌아온다 |
| DirectionalLight | Movable | 실시간 낮 → 노을 → 밤 전환 |

![최종 결과 — 밝고 평평한 툰 룩이 그대로 유지된다](/assets/img/posts/2026-07-20/lobby_hybrid.png)

중간에 조명을 Static으로 돌렸다가 한 번 크게 헤맸다. **Static 라이트는 실시간으로 렌더되지 않는다** — 라이트맵에만 존재하기 때문에 캐릭터가 그 밑을 지나가도 빛을 받지 못하고, 라이트 자체가 꺼진 것처럼 보인다. 경고를 없애는 데만 집중하다 게임플레이 영향을 놓친 판단이었다.

돌아보면 이 프로젝트는 처음부터 라이트맵을 구울 이유가 없었다. 툰 셰이딩이 라이팅을 덮어써서 구운 디테일이 화면에 거의 반영되지 않고, 실시간 시간대 전환을 쓰는데 구운 조명은 한 시점에 박제된다. 게다가 구울 때마다 맵마다 수십 MB짜리 `_BuiltData` 바이너리가 생겨 머지 충돌 위험도 늘어난다. **"경고가 떴으니 없애자"가 아니라 "이 경고가 우리에게 의미가 있나"를 먼저 물었어야 했다.**

## 4. 오후 — 로비에서 스테이지로 입장이 안 된다

증상이 대칭적이었다. **내가 방을 만들면 내가 로딩 중에 튕기고, 상대가 방을 만들면 내가 로딩 화면에서 멈춘다.** 항상 문제가 생기는 쪽이 있었다.

로딩 게이트 구조부터 봤다. 클라이언트가 맵 로딩을 마치면 서버에 `ServerReportMapLoaded()`를 보내고, 서버는 **전원이 보고해야만** 게이트를 열어 카운트다운을 시작한다. 그런데 이 보고는 트래블 직후 `BeginPlay()`에서 **딱 한 번** 발사된다. 그 시점엔 해당 PlayerController의 액터 채널이 아직 완전히 열리지 않아 RPC가 유실될 수 있다. 게다가 예전에 있던 강제 시작 폴백이 제거된 상태라, 보고 하나가 유실되면 전원이 영구 대기한다.

보고를 멱등으로 만들어 서버 응답이 올 때까지 재전송하게 고쳤다. 다만 이건 안전망이고, **진짜 범인은 따로 있었다.**

커밋 이력을 훑다 "로딩 창 버그 해결"에서 추가된 코드를 발견했다.

```cpp
// 로비 대기 시간을 이용해 스테이지 맵을 백그라운드로 미리 로드해 둔다
LoadPackageAsync(MapPath, ...);
```

로딩 히치를 줄이려는 최적화다. 의도는 좋은데, **맵 패키지는 일반 에셋과 다르다.** 곧이어 실행될 `ServerTravel`의 `LoadMap`이 바로 그 패키지를 다시 여는 대상이라, 미리 올려둔 `UWorld`가 트래블 경로와 충돌한다.

그리고 이 프리로드는 `LobbyGameMode::InitGameState`에서 호출된다 — **게임모드는 서버에만 존재하므로 호스트에서만 실행된다.** 증상이 비대칭이었던 이유가 여기 있었다. 호스트는 자기 프로세스에서 충돌이 나 로딩 중에 이탈하고, 클라이언트는 멀쩡히 기다리다가 죽은 호스트 때문에 로딩에서 멈춘다.

호출을 걷어내고, 왜 껐는지와 대안(맵이 아니라 그 맵이 쓰는 머티리얼·텍스처만 개별 프리로드하거나 PSO 워밍업)을 주석으로 남겼다.

## 5. 덤 — 에셋이 죽어 있었다

로그에 이런 에러가 계속 찍혔다.

```
LogAssetRegistry: Error: Package is unloadable: .../SM_bed_001_003.uasset
  Reason: Invalid value for PACKAGE_FILE_TAG at start of file.
```

파일을 열어보니 에셋이 아니었다.

```
version https://git-lfs.github.com/spec/v1
<<<<<<< HEAD
oid sha256:dc2c43df69f1b2cac...
size 93943
=======
oid sha256:04e4e78171d9949b6...
```

**Git LFS 포인터 안에 머지 충돌 마커가 그대로 커밋돼 있었다.** 이 저장소는 `.uasset`·`.umap`을 전부 LFS로 관리하는데, 누군가 바이너리 파일의 충돌을 텍스트처럼 남겨둔 채 커밋한 것이다. 포인터가 깨졌으니 LFS가 실제 파일을 못 받고, 언리얼은 이 텍스트를 에셋으로 읽으려다 실패한다. 원격에도 깨진 채로 올라가 있어 팀 전원이 이 파일을 못 쓰는 상태였다.

`.uasset` 같은 바이너리는 머지 자체가 불가능하다. 충돌이 나면 **반드시 한쪽을 통째로 선택**해야 한다(`git checkout --ours` / `--theirs`). 충돌 마커를 남기면 파일이 조용히 죽는다.

## 오늘 배운 것

- **경고에 뜬 것만 고치면 절반만 고친 것이다.** 겹침 경고는 가장 심한 14개만 보여줬지만 실제로는 레벨 전체가 같은 문제였다.
- **품질 설정을 올려도 안 고쳐지면 원인이 거기 없는 것이다.** 샘플을 8배로 늘려도 그대로였을 때 방향을 틀었어야 했는데, 두 번 더 굽고 나서야 격리 실험으로 넘어갔다.
- **비대칭 증상은 코드 경로의 비대칭을 가리킨다.** "호스트만 튕긴다"는 곧 "호스트만 실행하는 코드가 있다"였고, 실제로 게임모드에만 있는 호출이 범인이었다.
- **최적화는 그것이 만드는 새 상태를 함께 봐야 한다.** 맵을 미리 로드하는 것 자체는 합리적이지만, 그 맵이 곧 트래블 대상이라는 맥락에서는 충돌이 된다.
